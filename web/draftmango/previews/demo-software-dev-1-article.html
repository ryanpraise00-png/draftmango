Why we still write the architecture doc first.

Two pages, one afternoon, and the cheapest bugs we'll ever fix.

Liam BrennanPrincipal Engineer
Published
9 October 2026
Reading time
7 minutes

ArchitectureProcessDocs

Every project at Draftmango starts the same way. Before a single line of production code, the tech lead writes a two-page architecture doc and the whole team argues with it for an afternoon.

It sounds old-fashioned. Agile teams are supposed to discover the design as they go, and a document feels like the waterfall we all escaped. But after 320 products, the doc is the one habit we would never drop — because the bugs it catches are the most expensive ones we know.

What goes in the doc

Not much. The template fits on one screen, and most sections take a paragraph:

  • The problem in the client's words, not ours.
  • The boundaries — which systems we own, which we only talk to.
  • The data — where it lives, who writes it, how long we keep it.
  • The risks we can already see, ranked by how much they would cost.
  • What we won't build, so nobody assumes we will.

The decision record

Every choice that would be painful to reverse gets one short entry. We keep them in the repository, next to the code they explain:

# ADR 004 — Scheduling API in front of the clinic systems
Status:   accepted, 2026-02-11
Context:  four booking systems, none with a public API
Decision: one REST API, an adapter per system
Cost:     +3 weeks now; no app change when a clinic migrates
# Revisit if a system gets a vendor API

The doc isn't there to be right. It's there to be wrong early, on paper, where fixing it costs an afternoon.

Why an afternoon beats a sprint

On the Harbor Health app, the review caught that two of the four clinic systems stored appointment times without a time zone. Found on paper, it was a one-line note in the adapter design. Found in production, it would have been patients arriving an hour early in March.

Keeping it alive

A doc nobody updates is worse than no doc. Ours lives in the repository, changes go through pull requests like code, and the tech lead re-reads it at every sprint planning. When the doc and the code disagree, one of them gets fixed that week.

In short Two pages, one afternoon, every project. Write down the problem, the boundaries, the data, the risks and what you won't build — then let the team tear it apart.
